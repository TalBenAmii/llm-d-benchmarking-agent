llm-d Benchmarking Assistant

Tal Ben Ami

THE PROJECT

From a benchmark goal
to an explained result

A conversational assistant for running llm-d benchmarks without first learning the entire toolchain.

“Benchmark a chat workload, compare two configurations, and tell me which meets my latency target.”

Understand

Interview the user, inspect the environment and choose from the live catalog.

Run with visibility

Show plans and commands, obtain approval, stream progress and handle failures.

Explain with evidence

Read validated reports, compare outcomes and retain reproducible results.

Original contribution: the assistant, orchestration/analysis integration and MCP interface. Inference serving, benchmark harnesses and upstream skills are reused.

llm-d Benchmarking Assistant 04
WEB WORKFLOW

A complete benchmark session

  1. Interview and probe
    Clarify workload/SLOs; inspect the actual environment.
  2. Ground and plan
    Read catalog/skills; show a structured SessionPlan and capacity/readiness findings.
  3. Approve and execute
    Deploy or reuse a stack, smoketest and run; inspect the command trail or steer mid-turn.
  4. Analyze and follow up
    Explain report-backed metrics, save a baseline, compare, sweep, export or clean up.
Three different modes: synthetic app simulation; real kind/harness execution against a CPU inference simulator; real model inference on GPU hardware.

SIMULATE still runs read-only checks, requires approval for mutations and returns synthetic results. It still needs a Claude or ChatGPT login for chat.

llm-d Benchmarking Assistant 06
RESULTS & EXPERIMENTS

More than “the run passed”

Measure and compare

TTFT, inter-token latency, throughput and percentiles; A/B and cross-harness comparison; missing fields stay missing.

Explore trade-offs

Generate DoE treatments, run bounded parallel sweeps, identify SLO-feasible configurations and the Pareto frontier.

Remember and reproduce

Cross-session history, eleven trend metrics, provenance bundles, reproduction proposals and portable HTML exports.

Goodput is a percentile-derived upper-bound estimate. Different workloads or harnesses do not automatically produce a fair winner.

The dedicated autotuner was retired. Iterative goal seeking now uses the existing sweep/analysis tools and knowledge playbooks.

llm-d Benchmarking Assistant 07
ADDITIONAL DELIVERABLE

The MCP server I built

Shared tools, knowledge resources and workflow prompts.

Useful outside the web app

Claude Code can inspect, plan, benchmark and analyze using the same mechanisms and knowledge.

A thin adapter

stdio transport, per-connection ToolContext, progress notifications, resources and workflow prompts; no duplicated benchmark engine.

Approval moves to the client

Command execution relies on MCP tool permissions. Plan elicitation is used when available; its fallback accepts the inert plan.

Separate repository: github.com/TalBenAmii/llm-d-bench-mcp. Supported installation: local, single-user Claude Code. Other clients and shared HTTP transport remain future work.

Making runs observable
and recoverable

Kubernetes orchestration

Labeled Jobs, deadlines, fault classification, transient retries, dead-letter failures, bounded sweep parallelism and checkpoint/resume.

Operational visibility

Live logs/resources, Prometheus metrics, Grafana assets, structured logs and correlation IDs.

Usable application

Resumable chats, namespace grouping, busy indicators, approval cards, model/effort selection, token/cache counts, charts, sharing and guided next steps.

Installation and deployment

Host bootstrap, one-command kind deployment, full container/toolchain, Helm and RBAC.

The SDK-native cutover replaced the custom loop while keeping the application’s event/approval interface. This is a single-user proof of concept, not a multi-tenant benchmark service.

llm-d Benchmarking Assistant 10
PROJECT REFLECTION

What went well.
What was difficult.

What went well

Designing the system, coming up with a project plan and working in an organized way.

Main difficulty

Understanding the requirements thoroughly. The proposal contained conflicting or wrong information, which made it harder to know what the final scope should be.

How I responded

I explored ideas that looked compelling and tried to think about which additions would be useful to someone using the application.

Technical challenges

Version drift, reliable approvals/recovery, report units/comparability, deployment/authentication and stale documentation all required careful validation.

Submission refresh — Codex

Helped inspect code, update the architecture and guides, rebuild the presentation/ZIP, and verify an extracted installation in fresh Python environments.

Experience and lesson

Organized planning helped, but the proposal still contained contradictions. AI-generated plans and descriptions need verification against requirements, the implementation and runnable evidence.
